# Фактчекинг российских новостей
## 3. Подход и архитектура

Для проверки тезисов из российских новостей выбран **агент с внешним поиском и фиксированной последовательностью шагов**. Модель выделяет тезис, подбирает формулировки для Яндекса и Telegram, оценивает релевантность и извлекает свидетельства. Код запускает обе поисковые ветки, проверяет цитаты, объединяет перепечатки и собирает карточку с вердиктом.

[Схема от входного текста до карточки](news-architecture.html). Каждый блок раскрывает метод, входные данные и пример структурированного выхода.

### Обоснование выбора

| Подход | Что даёт и чем ограничен |
|---|---|
| Поиск по одному шаблону | Дешёвый и воспроизводимый базовый вариант. Может пропустить документ, если редакция или канал описали событие другими словами. |
| RAG с собственным векторным индексом | Удобен для повторного поиска по накопленному архиву. Для свежих новостей требует регулярно загружать публикации и обрабатывать правки. |
| Агент со свободным числом шагов | Может дольше искать редкое свидетельство. Время проверки, стоимость и условия остановки сложнее предсказать. |
| Выбранный вариант | Обе ветки выполняют первый поиск. Если остался конкретный пробел, агент получает один дополнительный раунд. Это позволяет измерить, сколько доказательств дала переформулировка и во сколько обошёлся повтор. |

### Сквозной маршрут

1. **Текст → Claim.** Вход — `input_text`, `as_of`, при наличии `source_url` и `published_at`. Модель возвращает цитату, позиции, атомарную формулировку, вид высказывания и условия проверки. Код сверяет исходную подстроку. Из «поездок стало на 20% больше, это успех» получаем факт и мнение. Относительную дату разрешаем по дате публикации. Пустой ввод даёт `invalid_input`; текст без тезисов — `completed` с пустым массивом.
2. **Claim → QueryPlan.** LLM строит отдельные формулировки. Сохраняем неизменяемый тезис и условия, которые нужно проверить. Каждому запросу присваиваем цель: исходные данные, альтернативное описание, исправление или недостающий факт. Код ограничивает количество, удаляет повторы и запрещает модели добавлять хосты или каналы в реестр. Перефразировка может опустить заявленную цифру для поиска альтернативы. При оценке доказательств число возвращается как обязательное условие.
3. **Два обязательных поиска → Candidate.** Запускаем обе ветки в первом раунде. Яндекс ищет по всему вебу. Из XML-выдачи берём URL, заголовок и сниппет; нормализуем hostname, оставляем точные совпадения с реестром X хостов, проверяем каждый редирект. Загружаем выбранные страницы: HTTP + Beautiful Soup для HTML, отдельный обработчик для текстового PDF. API конкретного издателя — открытый вопрос. Для Telegram пользователь авторизует клиентскую сессию, а адаптер выполняет `messages.search(peer, q, min_date, max_date, limit)` для каждой формулировки в каждом из K каналов реестра. Сохраняем пару `channel_id/message_id`, ссылку, доступные даты публикации и редактирования и признаки пересылки. Пустой ответ, недоступный канал и ограничение частоты запросов получают разные статусы. [Yandex Search API](https://aistudio.yandex.ru/ru/docs/search-api/concepts/web-search) · [Клиентская авторизация Telegram](https://core.telegram.org/api/auth) · [Поиск сообщений](https://core.telegram.org/method/messages.search)
4. **Кандидаты → RelevanceDecision.** Критик получает тезис, обязательные условия, прочитанный текст статьи или пост с контекстом. Для таблицы получает заголовки и единицы. Решение по каждому материалу — `keep`, `reject` или `uncertain`. Явно другой объект, территория или событие допускают отказ с конкретным основанием. Источник с опровержением, иным числом или прямым исправлением сохраняем. Недостаток контекста отправляет материал в `uncertain`: берём соседний абзац, исходный пост или используем это как пробел для второго раунда. Критик не видит исторические веса источников. Сниппет и низкий вес сами по себе не достаточны для исключения. Ручная выборка отклонений проверяет, насколько критерии действительно воспроизводимы.
5. **Пробел → перепланирование.** Причины разделяем: выдача пуста, все хосты отфильтрованы, критик отклонил материалы, отсутствует базовый период, конфликт версий, техническая ошибка. Если R1 оставил пробел, LLM видит прежние запросы, число попаданий в каждом канале, коды отказа и формирует существенно иной R2 для одной или обеих веток. При первом запросе только по аббревиатуре ищем полное название и местный топоним. При техническом отказе используем допустимую повторную попытку в рамках бюджета. Бесполезную перефразировку сетевой ошибки не запускаем. После R2 останавливаемся.
6. **Текст → Evidence → SourceVote.** Отдельный шаг модели определяет, что именно утверждает публикация: поддерживает тезис, оспаривает или даёт только контекст. Код сверяет дословную цитату, URL/ID, координаты и арифметику. Сравниваем дату версии с датой среза. Пересылки и почти дословные перепечатки связываем с одним первоисточником по явной ссылке, метаданным и совпадающим фрагментам. Если газета лишь передала слова ведомства, её материал подтверждает факт заявления; самостоятельное измерение требует собственного свидетельства. Независимость неясна — фиксируем неопределённость происхождения и проверяем устойчивость вывода без этой группы.
7. **SourceVote → агрегация → VerdictCard.** Применяем прозрачное правило или ранее обученную модель. Для содержательного вердикта нужны проверенная цитата, покрытие существенных условий, успешная обязательная проверка обоих направлений и отсутствие неразрешённого существенного конфликта. Прямой документ, обнаруженный в одной ветке, может быть достаточным, когда вторая ветка успешно выполнена и вернула ноль. Довод «поиск ничего не нашёл» не опровергает тезис.

**Условие реализуемости Telegram.** Каналы входят в обязательный охват продукта. Пользовательская сессия даёт технический доступ к доступным каналам. Условия Telegram отдельно ограничивают использование материалов платформы в AI-системах и описывают узкую возможность исключения при явном продолжающемся согласии всех затронутых пользователей в конкретном контексте. Для пилота требуется установить применимость этого условия и основания по каждому подключаемому каналу, включая передачу текстов критику и использование в оценке. В рабочем процессе без подходящего основания ветка получает `policy_blocked`; сбор и обработка таких сообщений не выполняются. Это блокирует полноценную проверку и приёмку двухканального MVP. Для отладки переходов подходят собственные тестовые сообщения, созданные командой вне платформы; они не подтверждают работоспособность интеграции. [Telegram API Terms §1.5](https://core.telegram.org/api/terms) · [Условия лицензирования контента](https://telegram.org/tos/content-licensing)

### Бюджет одного проверяемого тезиса

K — число каналов обязательного реестра в данном запуске. Значения предложены для пилота. За раунд критик обрабатывает отобранные материалы пакетом. Отдельный пакет извлекает доказательства только из прошедших материалов.

| Стадия | Яндекс | Telegram | Модель |
|---|---|---|---|
| Общий разбор новости | — | — | 1 извлечение на текст, помещающийся в контекст |
| R1 | До 3 запросов, до 5 URL на запрос, до 4 попыток чтения | До 2 вариантов × K каналов, до 5 попаданий на пару «запрос, канал». Для чтения выбираем до 4 постов суммарно с учётом разнообразия каналов | 1 план + до 1 вызова критика + до 1 извлечения доказательств |
| R2, если есть конкретный пробел | До 2 новых запросов и до 3 новых попыток чтения | До 1 нового варианта по нужным каналам, максимум K поисков и до 3 новых постов | 1 новый план + до 1 критика + до 1 извлечения |
| Верхняя граница двух раундов | 5 запросов, 7 чтений | 3K поисковых вызовов, до 7 отобранных постов | До 6 логических вызовов на факт сверх общего разбора |

При K = 4 верхняя граница — 5 обращений к поиску Яндекса и 12 поисковых обращений к Telegram. Получение контекста поста — отдельная операция чтения. Повторы расходуют соответствующий лимит. Необработанная часть обязательного реестра указывается в покрытии; счётчики различают попытки, уникальные запросы и успешные ответы. Число модельных вызовов дано для одного пакета на стадию; переполнение разбиваем на пакеты и учитываем фактический расход. Для мнения и непроверяемой фразы дополнительных вызовов нет.

### Как применить EM к источникам

**Единица наблюдения.** Строка матрицы — отдельный тезис на конкретную дату. Столбец — устойчивый ID первоисточника: издатель, ведомство или канал, который сам сделал утверждение. Значение — подтверждает или опровергает по проверенной цитате. На пару «тезис, первоисточник» допускаем один голос. Репост того же пресс-релиза на двух сайтах и в трёх каналах остаётся одним свидетельством. Исправление учитываем по версии на дату среза; неразрешимое внутреннее противоречие сохраняем в карточке и пропускаем как однозначный голос. Нерелевантный текст, пересказ без собственной позиции и молчание дают пропуск. Роль наблюдателя принадлежит первоисточнику, а не критику, запросу или адаптеру доставки.

**Обучение вне пользовательского запроса.** На исторических событиях собираем разреженные голоса, примеры обоих направлений и человеческие опорные метки. Пары сравниваем только при наличии перекрытия: несколько независимых источников освещали одни и те же тезисы. У модели Dawid–Skene для каждого источника есть матрица вероятностей наблюдаемой позиции при каждом истинном классе. E-шаг оценивает вероятности классов тезиса при текущих матрицах. M-шаг обновляет матрицы по ожидаемым счётчикам. Предлагаем сглаживание и зафиксированные человеческие опорные метки на обучении, чтобы задать ориентацию классов. Такие дополнения к базовому EM явно версионируем. На новом тезисе делаем только расчёт с замороженными параметрами. [Dawid & Skene, 1979](https://doi.org/10.2307/2346806)

| Вариант | Что оценивает | Когда полезен |
|---|---|---|
| Прозрачное правило и равные голоса | Общее правило достаточности, прямота свидетельства и один голос на независимое происхождение. При равенстве голосов отмечаем конфликт. | Стартовая версия и контроль. Работает без истории. |
| One-Coin Dawid–Skene | Одна вероятность правильной позиции источника; для двух классов ошибка считается симметричной. | Более экономная модель при скромной истории. Не выявляет, что источник чаще ошибается только в одном направлении. |
| Полный Dawid–Skene | Две условные вероятности для бинарной задачи; источник может по-разному ошибаться при поддержке и опровержении. | Проверяем при достаточном числе пересечений и покрытии обоих классов. Источник с редкими наблюдениями использует сглаженную групповую оценку либо базовое правило. [Реализации вариантов Dawid–Skene](https://crowd-kit.readthedocs.io/en/stable/classification/) |

Для известных источников рассчитываем `P(z | голоса) ∝ P(z) × произведение P(голос_s | z, источник_s)`. Произведение предполагает условную независимость. Совместные ошибки редакций, одна ошибочная извлекающая модель и избирательное освещение подрывают это предположение. Поэтому для каждой версии храним объём наблюдений, число пересечений и устойчивость при исключении одной группы; для нового, редкого или несвязанного источника показываем отсутствие индивидуальной оценки. Никаких заранее назначенных процентов «надёжности Telegram» и «надёжности сайта».

**Переход к трём вердиктам.** Латентный класс EM бинарный. «Недостаточно данных» — решение о достаточности доказательств. Для режима EM на валидации подбираем две границы для вероятности поддержки и калибруем уверенность. Средняя зона, отсутствие достаточной цитаты или неразрешённый конфликт ведут к воздержанию. При истории, недостаточной для надёжного сравнения, карточку строим базовым правилом с указанием метода. Числовую вероятность непроверенной модели пользователю не показываем.

### Структурированные ответы и проверка контрактов

Предлагаемый механизм — типизированные модели с JSON Schema, обязательными полями, enum и проверкой ссылочной целостности в коде. LLM не создаёт URL: она выбирает ID реально полученных материалов. Формат и дословность цитаты проверяются отдельно от обоснованности вывода. Невалидная запись не попадает в агрегатор. Ошибка обязательной стадии, не исправленная в бюджете, даёт технический статус с указанием стадии.

| Контракт | Обязательные поля и ограничения |
|---|---|
| Claim | `claim_id, quote, span, text, kind, slots`. Границы цитаты совпадают с исходным текстом, `kind ∈ {fact, opinion, unverifiable}`. |
| QueryPlan | `claim_id, round, yandex[], telegram[], gap`. Каждый вариант содержит `q, intent`. У факта R1 обе ветки непусты. Для R2 указан конкретный пробел. Реестры добавляет код. |
| Candidate | `id, branch, source_id, locator, query_id, retrieved_at, retrieval_status`. У веба — URL, у Telegram — ID канала и сообщения. Поиск и чтение логируются отдельно. |
| RelevanceDecision | `candidate_id, decision, reason_code, rationale`. Решение `keep / reject / uncertain`; для отказа проверяемое несовпадение, для сомнения — чего не хватает. На каждый прочитанный кандидат одно решение. |
| Evidence | `id, candidate_id, claim_id, quote, location, stance, origin_id, conditions, source_assessment`. Позиция `supports / refutes / context`; локатор и цитата проверяемы по сохранённой версии. |
| SourceVote | `claim_id, observer_id, origin_group, label, evidence_ids[]`. Направление `supports / refutes`, максимум один голос на независимый первоисточник; пропуски не порождают запись. |
| Aggregate | `method, model_version, p_support, coverage, gaps[]`. У базового правила вероятность null. Покрытие содержит статусы веба и каждого обязательного канала. |
| VerdictCard | `claim_id, quote, kind, status, verdict, confidence, confidence_reason, evidence_for[], evidence_against[], limitations[], coverage, method, trace_ids[]`. Для пометки и сбоя вердикт null. Каждая ссылка восстанавливается из ID проверенного доказательства. |
| Output | `document_id, as_of, status, cards[], trace[]`. Журнал содержит фактические действия, версию реестров, запросы, отклонения, ошибки, число раундов и причину остановки. |

**Пример прохождения, условные данные.** Новость утверждает: «В городе Н в 2024 году совершили на 20% больше поездок, чем в 2023-м». Для веба LLM формирует «город Н общественный транспорт пассажирские поездки отчёт 2023 2024», для каналов — «поездки итоги года» и «перевезли пассажиров». Критик сохраняет пост с цифрой 12% для того же города и периода; статью о росте числа маршрутов отклоняет с `wrong_metric`. Пост ссылается на веб-отчёт: это одна группа. R2 ищет «уточнённые итоги перевозок» и базовый год. Если таблица даёт 100 и 112 млн поездок по одной методике, карточка опровергает 20% и показывает расчёт 12%. Если осталась только цифра по соседнему городу, вывод — «недостаточно данных». При блокировке обязательной ветки — «проверка не завершена».

**Выходы.** Содержательные варианты — подтверждается, опровергается, недостаточно данных. Для мнения или непроверяемой формулировки возвращаем отдельную пометку без поисковых раундов. Ошибка модели, недоступная обязательная ветка или блокировка доступа дают `incomplete` с частичными материалами, без финального фактического вердикта. Статус новости отражает завершённость её карточек, включая `partial` при смешанном результате.

## 4. План оценки

**Основной набор.** Начинаем с 20–30 российских новостей разных редакций и тематик, с фактами обоих направлений, мнениями, исправлениями и перепечатками. На дату среза два разметчика независимо выделяют тезисы, устанавливают эталон, сохраняют подтверждающие и опровергающие цитаты, первоисточники и пригодные документы/посты. Разбирают расхождения до финального прогона. Реестры, версии текстов, разметку права использования Telegram-материалов и дату фиксируем. Собственные синтетические посты помечаем и оцениваем отдельно. FEVER можно использовать только для контрольного теста англоязычной верификации. [FEVER](https://fever.ai/dataset/fever.html)

Такого пилота достаточно для разбора ошибок процесса; пригодность данных для обучения весов определяем отдельно. Для EM нужен исторический набор с повторяющимися источниками и пересечениями. Показываем распределение голосов и пересечений по источникам, число независимых групп и покрытие двух классов. Обучение, подбор порогов и финальная проверка разнесены по событиям и времени. Все версии и перепечатки одного события остаются в одной части. Веса, реестры и пороги замораживаем до теста.

| Что проверяем | Как считаем и с чем сравниваем |
|---|---|
| Извлечение | Полнота и точность атомарных тезисов относительно ручной разметки; доля мнений, ошибочно отправленных на поиск. |
| Планирование запросов | При одинаковом бюджете сравниваем шаблон, LLM-варианты в R1 и LLM-варианты с R2. Для веба, Telegram и их объединения измеряем долю тезисов с хотя бы одним достаточным набором материалов в пределах бюджета. Для R2 отдельно считаем, сколько тезисов он спас после нулевого R1. |
| Критик | На размеченных парах «тезис, кандидат» измеряем точность и полноту сохранённых релевантных материалов; отдельно считаем долю ошибочно отклонённых опровержений. Показываем частоту uncertain и её исход. Сравнение с вариантом без критика — на одной замороженной выдаче. |
| Агрегация | При одинаковых цитатах, группах происхождения и правилах достаточности сравниваем базовый вариант, One-Coin и полный DS. Отдельно показываем результаты на знакомых и новых источниках. Проверяем влияние удаления перепечаток и исключения крупнейшего источника. Для бинарных вероятностей на определимых тезисах считаем Brier score и сопоставляем заявленную уверенность с точностью. |
| Пользовательский результат | Точность трёх вердиктов и macro-F1; в сквозной точности незавершённая проверка факта входит в знаменатель как промах. Доля корректных ссылок — доля пар «довод, ссылка», где цитата обосновывает довод в заявленном направлении. Доля полностью верных карточек — извлечённые факты с правильным вердиктом и достаточной проверенной цитатой среди всех эталонных определимых фактов. |
| Покрытие и стоимость | Доля тезисов с выполнением обеих веток и всего списка K; отдельно успешная пустая выдача, ошибки доступа, `policy_blocked`, доля воздержаний. По раундам измеряем число запросов, прочитанных кандидатов, токены, стоимость и p50/p95 задержки. |

Экспериментальный вес включаем в итоговый продукт, если при сопоставимом покрытии он улучшает результат на отложенных событиях, сохраняет качество ссылок и даёт приемлемую калибровку. Публикуем абсолютные числа вместе с долями и неопределённость по событиям. Состав X и K, права и доступ по каналам, парсеры конкретных сайтов, доступность API издателей, глубина выдачи и достаточный объём истории для EM остаются открытыми инженерными вопросами.
